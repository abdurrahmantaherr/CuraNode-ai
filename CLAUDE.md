# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Development Commands

### Setup
```bash
uv sync                                    # Install dependencies
cp .env.example .env                       # Fill in your Supabase project's URL/keys/DB connection string
uv run python backend/ops/scripts/seed_synthetic.py   # Create demo accounts in Supabase Auth + app rows
uv run python backend/ops/scripts/purge_cancelled_files.py   # dry run: files left behind by old discards (add --apply to remove)
```

The database is shared, so setup never runs `alembic upgrade`: applying migrations is the schema owner's job (see "Database Management" below).
A working local environment needs no migration: the shared database already has the schema, so once `.env` is filled in, start the app (below); the test suite needs no database at all (in-memory SQLite built from the models).

Google sign-in is optional and off by default (`OAUTH_ENABLED=false`). To enable it, set `OAUTH_ENABLED=true` and `SUPABASE_ANON_KEY` in `.env`, enable the Google provider in the Supabase dashboard (Authentication → Providers), and add `{PUBLIC_BASE_URL}/auth/callback` to Authentication → URL Configuration → Redirect URLs. See "OAuth (Google sign-in)" below before touching anything under `backend/app/identity/oauth.py` or the OAuth routes in `web/router.py`.

### Running the Application
```bash
uv run backend/app/main.py                 # Start the development server
# Access at http://127.0.0.1:8000
```

### Database Management
This project's Supabase Postgres database is **shared** with the wider CuraNode-AI product — most tables (`user_profile`, `clinic`, `patient`, `doctor`, `clinic_staff`, `doctor_affiliation`) are pre-existing and owned by that larger schema, not by this repo; so are `allergy`, `chronic_condition`, `consent_grant` and `access_log`. Only `audit_log` and `patient_medication` are created here (plus additive columns and indexes on shared tables). The medical-documents work adds: lifecycle / OCR columns on `document` (`c3a91d7e5f20`); `ocr_extraction.row_index`; `'doctor_entry'` in `ocr_job.engine`'s CHECK (`35c4bc13fa37`, for a doctor-written prescription); `ocr_job.ai_sections`, a nullable JSONB (`b7e24c19a053`); and a WIDENED `ocr_extraction_field_name_check` — 8 names -> 28 (`e3a52c8d7f14`, a strict superset; no table or column added). These four were applied to the shared database by the document / OCR work, so `alembic upgrade` has nothing left to do for them there — but all four migration files must be in the repo (they replaced the reconstructed placeholders), or `alembic` fails with "Can't locate revision". `uv run alembic heads` must show exactly one head; what the database itself is at is the schema owner's to check (see the rules below).

```bash
# Safe on a dev machine: none of these connect to a database. Use a dummy URL so
# nothing can reach the shared DB by accident.
export DATABASE_URL=postgresql+asyncpg://offline:offline@127.0.0.1:9/offline
uv run alembic heads                       # Must print exactly ONE head
uv run alembic history                     # Must be linear
uv run alembic upgrade <from>:head --sql   # Offline SQL for review; nothing is executed
uv run alembic revision -m "description"   # Create a new migration file, then HAND-WRITE it
```

Migrations in this repo are **additive-only and hand-written**, never autogenerated: `alembic revision --autogenerate` would try to diff against and recreate tables this repo doesn't own. When a change is needed, add columns/tables explicitly in the migration body, matching the pattern in `alembic/versions/6feacefae2d0_*.py`.

Rules for the migration chain:
- **Migrations are never run against the shared DB from a dev machine.** `alembic upgrade`/`downgrade`/`stamp` (and `current`, which connects) against the shared database are done only by the schema owner. A revision or step marked **"ASK ME BEFORE RUNNING"** needs the schema owner's explicit go-ahead.
- **The chain has exactly one head.** Every new revision's `down_revision` is the current output of `alembic heads`; a second head is a bug to fix before merging (re-parent the newer branch's first revision). `tests/test_privacy_access.py::test_ac29_revision_chain_is_single_and_unbroken` pins the chain.
- **Don't trust a revision id written in a doc** (including this one) as "the shared DB's current revision". The repo's head comes from `alembic heads`; what the shared DB is at is checked read-only by the schema owner.
- Another codebase (document/OCR work) migrates the same database through the same `alembic_version` table. When the shared DB turns out to be at a revision this repo has no file for, add a **reconstructed placeholder**: a no-op `upgrade()`, a `downgrade()` that refuses, and a docstring with the DDL recovered read-only from `pg_stat_statements` and the evidence for its parent. Then chain this repo's revisions after it. Two exist so far: `35c4bc13fa37` and `b7e24c19a053`, both standing in for OCR-codebase revisions whose files this repo doesn't have. `e3a52c8d7f14` is the OCR codebase's real file, kept unchanged; P9's `dba968144fb4` is chained after it. When a real upstream file turns up, replace its placeholder with it, unchanged.

### Key Architectural Decisions

1. **Authentication & Session Management**
   - **Identity is fully delegated to Supabase Auth** — this codebase never hashes a password or signs a session token. `identity/security.py` talks to Supabase's Auth API server-side only (service-role key, never exposed to templates/JS).
   - Access tokens are Supabase-issued JWTs, verified **locally** against the project's public JWKS (asymmetric ES256 signing keys — not a shared HS256 secret). `decode_supabase_access_token` in `identity/security.py` yields only a `user_id`; nothing else is trusted from the token.
   - **Two separate Supabase client lifecycles matter and must not be conflated**: `get_supabase_client()` returns a process-wide singleton used only for `auth.admin.*` calls; `new_auth_client()` builds a fresh, single-use client for every `sign_in_with_password`/`refresh_session`/`exchange_code_for_session` call. The SDK's client is stateful — signing in mutates the client's session and starts a background auto-refresh timer — so sharing one instance across users, or between a sign-in and a later admin call, corrupts it (observed in practice as `AuthApiError: User not allowed` on a subsequent admin call).
   - A Postgres trigger (`on_auth_user_created`) auto-inserts a default `user_profile` row the instant a Supabase auth user is created. `identity/service.py`'s `register()` fetches and *updates* that row rather than inserting a second one.
   - Refresh tokens are single-use; rotation and reuse-family revocation are handled by Supabase Auth itself.
   - Role verification happens per-request from the database (never from the token) for immediate revocation — five explicit dependencies in `deps.py`: `ActorDep`, `PatientDep`, `VerifiedDoctorDep`, `DoctorDep` (any doctor, verified or pending — only for the doctor's own schedule (D7), which exposes no patient data) and `ClinicAdminDep`. No ad-hoc role checks anywhere in the codebase.
   - Login lockout (10 failures / 15 min) is tracked app-side against `user_profile.failed_logins`/`locked_until`, checked *before* Supabase is ever called, so it's independent of Supabase's own abuse protection.

2. **OAuth (Google sign-in)**
   - Off by default (`OAUTH_ENABLED=false`); a fail-fast guard requires `SUPABASE_ANON_KEY` when it's turned on. Server-side PKCE only — the browser never sees a token. All of it lives in `identity/oauth.py` and the OAuth/onboarding routes in `web/router.py`.
   - **Supabase's `/authorize` endpoint does not accept a caller-supplied `state` query param** — confirmed by reading the real SDK's `AsyncGoTrueClient._get_url_for_provider`, which sends only `provider`/`redirect_to`/`code_challenge`/`code_challenge_method`. GoTrue manages its own internal state for the round trip to the provider; a client-supplied `state=` collides with that and comes back as `error_code=bad_oauth_state` (reproduced against a live project). This app's own CSRF-binding state instead rides **inside** `redirect_to`'s own query string — never as a sibling param to `authorize_url()`.
   - The `on_auth_user_created` trigger fires for OAuth signups too, defaulting `role='patient'` — `service.login_with_oauth()` must **update** that row, exactly like `register()` does, never insert a second one.
   - A brand-new OAuth user is never auto-assigned a role: `Doctor.pmdc_number` is `UNIQUE NOT NULL` and a patient's passport number is permanent, so guessing wrong would be unfixable. Instead `deps.py`'s `Actor.onboarding_complete` gates every dashboard route until `/{locale}/onboarding` is completed.
   - An email Google returns that already belongs to a *different* `user_profile` row is refused and the freshly-issued Supabase session is revoked (`service.login_with_oauth`) — an unverified provider email must never take over a password account.
   - The state cookie (`cn_oauth_state`) is `SameSite=Lax` — it must survive the cross-site return hop from Google via Supabase. Session cookies stay `Strict`; a same-site interstitial template (`auth/oauth_complete.html`) bounces the browser through one same-site request first so `Strict` cookies aren't dropped on arrival.

3. **Patient profile (FR2)**
   - `backend/app/profile/` (`schemas.py`, `service.py`, `router.py`) owns all business logic. The JSON API (`/api/v1/me/profile`, `/api/v1/me/{allergies,conditions,medications}`) and the server-rendered page (`/{locale}/patient/profile`, handlers in `web/router.py`) both call the **same** service functions — no rule is implemented twice.
   - **The app connects to Postgres as `postgres` with BYPASSRLS**, so Supabase RLS policies on `allergy`/`chronic_condition`/`patient_medication` do **not** protect these queries. Every entry lookup in `profile/service.py` filters by the caller's own `patient_id` in application code; RLS exists only to protect the Supabase Data API, a door this app doesn't use.
   - Entries are **never hard-deleted**: allergies and medications get `removed_at` set, and a chronic condition moves to `status='resolved'`. An entry is editable **iff** `recorded_by == caller's user_id` — `NULL` (legacy) and another user's id are both read-only, shown as "Recorded by a clinician". This errs toward patient safety: a patient can never erase a clinician-recorded entry.
   - A foreign, nonexistent, or inactive-for-PATCH entry id all raise the identical `NotFound` — ids must never be distinguishable by probing.
   - Every successful mutation writes exactly one `audit_log` row in the same transaction (`profile.update`, `profile.<kind>.add/update/remove`). Basic-detail changes log only `fields_changed`, never values (identity PII); entry changes also log `before`/`after` clinical field values, except `notes`, which is free text that may hold PII and is logged only by name.
   - Business-rule numbering (`BL-01`…`BL-36`) and acceptance criteria (`AC-01`…`AC-26`) live in `.claude/specs/patient_profile_spec.md` — read it before changing this feature; it is the source of truth over `docs/TDD.md` wherever they disagree.

4. **Privacy & access control (FR4, FR5 — P4 + P9)**
   - `backend/app/consent/` owns it: `service.py` (grants: grant/change/revoke/list/grantee search, plus the doctor-side lookup), `gateway.py` (the **only** door to another person's profile sections), `access_log.py` (the patient's FR5 view), `router.py` (`/api/v1/me/consents*`, `/api/v1/me/access-log`). The web page `/{locale}/patient/access` and the doctor page `/{locale}/doctor/patient/{id}` call the same functions.
   - **Grants are per section** (`basics`, `allergies`, `conditions`, `medications`, `prescriptions`, `lab_reports`, `visits` — `consent/schemas.py::SECTIONS`), stored in the shared `consent_grant.scope_sections`. `[]` means **nothing shared**. Durations: 24h / 7d / 30d (default) / until revoked. This amends TDD §3.4's all-or-nothing rule.
   - At most one unrevoked grant per patient/grantee (`uq_consent_grant_one_active`, plus a service check). Granting again while active returns the existing grant (200, no write); a lapsed grant is closed and linked via `replaced_by`. Changing sections never edits a grant: revoke (`revoked_by`) + insert + `replaced_by`. Grants are never deleted.
   - A clinic grant reaches every doctor with an **active** `doctor_affiliation` at that clinic. Doctor verification and affiliations are read live on every call (`service.live_doctor`).
   - **Every** read of another patient's `allergy`/`chronic_condition`/`patient_medication`/basics goes through `gateway.read_sections`/`read_section` with a mandatory `purpose`. It writes one shared `access_log` row per section read *before* returning data, in the same transaction. `tests/test_privacy_access.py::test_ac21_*` fails the build if any other module (besides `profile/service.py`, which reads only the caller's own rows) touches those models.
   - `ConsentDenied` subclasses `NotFound`: unverified, revoked, expired, empty-section, never-granted and nonexistent all give the identical 404 (D2). Clinic admins never pass (NFR16).
   - An unshared section is rendered "Not shared by patient", never as an empty list. Rules: `BL-01`…`BL-25` / `AC-01`…`AC-30` in `.claude/specs/privacy_access_spec.md` (wins over `docs/TDD.md` and the P4 `medical_passport_spec.md`).

5. **Doctor schedule (D7)**
   - `backend/app/schedule/`: `engine.py` (pure; standard library only), `schemas.py`, `service.py`. The web page `/{locale}/doctor/schedule` (handlers in `web/router.py`) calls the service; there is no JSON API yet.
   - **`engine.py` owns the single overlap definition** (`overlaps`: half-open, back-to-back allowed) and every window rule: R1 slot conflicts, R1b slot vs future extras, R3 effective availability (never merged, live cap inheritance), R4 extra vs every effective window (any clinic, the anchor included), R4b, the time-off row mapping and the extra's anchor. It returns conflicts as plain data; the service raises `ScheduleConflict` (409). Never re-implement overlap logic anywhere else.
   - Maps onto the shared `doctor_schedule` (a slot belongs to a `doctor_affiliation`) and `schedule_exception` (one per slot: `leave`/`emergency`/`extra`). D7's migration `291c06a2b86f` adds exception windows, `removed_at`, an extra's own `max_tokens`, and two `doctor_schedule` CHECKs; it is ASK ME BEFORE RUNNING on the shared DB.
   - Hospitals: a doctor ticks every hospital they work at when signing up (`clinic_ids`) and can add more later from the schedule page (`identity.service.add_doctor_clinics`). Both go through `identity.service.link_doctor_clinics` and create **active** `doctor_affiliation` rows at once — no confirmation step (owner's decision 2026-10-11, no hospital admins yet); re-adding a non-active link reactivates it. Consequence, accepted: a verified doctor who adds a hospital is immediately reached by that hospital's clinic consent grants (P9), exactly as with sign-up links — `tests/test_doctor_add_hospital.py` pins it.
   - Any doctor, verified or pending, manages their own schedule through `DoctorDep` / `_doctor_schedule_guard`, never `VerifiedDoctorDep`. Every query reaches the schedule tables through `doctor_affiliation` filtered by the caller's own `doctor_id` (BYPASSRLS). Foreign, unknown and removed ids are one `NotFound`.
   - Every write takes `SELECT … FOR UPDATE` on the caller's `doctor` row first (`service.lock_statement`), then checks and writes in one transaction, with one `audit_log` row per row written (`schedule.slot.*`, `schedule.exception.*`; an exception's `reason` is recorded only as `reason_length`). Rows are never deleted.
   - `get_effective_availability` is the only way to read availability (today up to 30 days). `appointment` is mapped read-only so R10 can count upcoming bookings; D7 never writes it.
   - Rules `R1`…`R14` and acceptance criteria `AC-1`…`AC-33` live in `.claude/specs/D7-multi-hospital-schedule.md` (wins over `docs/TDD.md` §3.7/§7.2); the plan is `.claude/plans/D7.plan.md`.

6. **Security Properties**
   - Password hashing is Supabase Auth's responsibility, not this codebase's.
   - Fail-shape-identical authentication errors (same response for wrong password/unknown email/suspended account). Exact response-*timing* parity is no longer guaranteed end-to-end, since password verification now crosses the network to Supabase's GoTrue service.
   - Registration is not an oracle (duplicate emails return success-shaped response and never call Supabase or create a row).
   - Account lockout after 10 consecutive failures (15-minute lockout). OAuth honours an existing lockout but never contributes to it — there's no password on that path to brute-force.
   - Startup guards prevent running without `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` (outside `test`), `OAUTH_ENABLED=true` without `SUPABASE_ANON_KEY`, or with non-synthetic data in non-pilot environments.

7. **Database schema is shared, not owned**
   - `user_profile`, `clinic`, `patient`, `doctor`, `clinic_staff`, `doctor_affiliation` are pre-existing tables belonging to the wider CuraNode-AI product's Supabase project. `db/models.py` maps onto their real column/table names (e.g. `Patient.passport_no` → column `passport_uid`; `Doctor` has no `primary_clinic_id` — clinic membership goes through the separate `DoctorAffiliation`/`doctor_affiliation` many-to-many table instead).
   - The clinic-admin role's **database value is `"admin"`**, not `"clinic_admin"` — the shared schema's CHECK constraint only allows `patient`/`doctor`/`staff`/`admin`. The Python enum member `UserRole.CLINIC_ADMIN` is unchanged; only `.value` differs.
   - Only `audit_log` and `patient_medication` are created and owned outright by this repo. Auth events and grant changes go to `audit_log`; reads of a patient's record go to the shared `access_log` (written only by `consent/gateway.py`). The P9 migration adds `revoked_by`, `replaced_by` and `uq_consent_grant_one_active` to the shared `consent_grant`. The patient-profile migration also adds provenance/soft-remove columns (`recorded_by`, `updated_at`, `removed_at`/`recorded_at`) to the shared `allergy`/`chronic_condition` tables — see "Patient profile (FR2)" above for the BYPASSRLS/soft-remove/editability rules that follow from this.
   - **Migration chain:** another codebase (document / OCR work) migrates the same database through the same `alembic_version` table. Its four revisions (`c3a91d7e5f20`, `35c4bc13fa37`, `b7e24c19a053`, `e3a52c8d7f14`) are in the chain as REAL files — they replaced the reconstructed placeholders that had stood in for them, and the DDL recovered into those placeholders matches. Run `uv run alembic heads` for the repo's head instead of trusting an id written here, and never `upgrade`/`downgrade`/`stamp` — or even `current`, which connects — against the shared DB from a dev machine; those are schema-owner-only (see "Database Management" for the full rules). P9's migration has so far only been run on SQLite.
   - **Reaching the database.** Found from a real dev machine on a slow, flaky route to a far-away pooler (Sydney; a query ~1 s, a TLS handshake 3-10 s, DNS that fails now and then, connections reset by the other end): the first request after the server idled failed with a 503 and the next one worked, the server twice failed to START, and every page paid ~1 s per query.
     - *Engine* (`db/session.py::engine_options`): ONE attempt at a NEW Postgres connection gets `DATABASE_CONNECT_TIMEOUT_S` (default 25 — asyncpg's own 60 s turned a blip into a minute-long hang, but 15 s made the server fail to start on a 10 s handshake), `statement_cache_size=0` for the Supabase poolers, `pool_use_lifo` (keep one warm connection busy instead of rotating through idle ones) and `pool_recycle=900`. SQLite gets none of these. **Do not add `pool_pre_ping`**: it tests every checkout, one more network round trip per request (a second on this route). Open pull request #8 (`zarwak`, `fix/db-stale-connections`) adds `pool_pre_ping=True, pool_recycle=300` and two tests pinning exactly those values; it overlaps `db/session.py` — whichever merges first, the other must keep THIS design (and replace those two tests with `tests/test_db_connection_guards.py`'s).
     - *Guards* (`install_connection_guards`): (1) a pooled connection that sat idle longer than `DATABASE_IDLE_PING_S` (default 15; 0 = off) is tested with `do_ping` as it is checked out and, if dead, raises `DisconnectionError` so the pool opens a fresh one — busy connections are never tested; reproduced on the real pooler by terminating a pooled connection (the next query raised `InterfaceError`; with the guard it succeeded). (2) Opening a connection is retried (`db/transient.py::connect_with_retry`: 3 attempts, within twice the timeout, growing pause) but ONLY for what a second try can fix (`is_transient_connect_error`: timeout, refused/reset/aborted, failed DNS, an `OSError` whose errno / WinError says network — e.g. WinError 121 — and asyncpg's server-side connection errors). A wrong password, a missing database or any other error is raised at once: retrying those would only hammer the server.
     - *Start-up* (`main._startup_checks`): the non-synthetic-data guard (BL-17) needs one connection, so it tries `STARTUP_DB_ATTEMPTS` times with a growing pause; the real-data refusal is never retried; if the database stays unreachable the server still refuses to start (the check cannot be skipped) but with a one-line message.
     - *503, not a bare 500* (`web/unavailable.py`): `is_database_unavailable` is deliberately narrow — SQLAlchemy `OperationalError` / `InterfaceError` / any `DBAPIError` with `connection_invalidated`, or a network error by `transient.is_network_error`. The handler is registered for the broad parents `HANDLED_BASES = (OSError, DBAPIError)` (Starlette picks handlers by class) and RE-RAISES anything that is not clearly an outage, so a `ValueError`, `FileNotFoundError` or `IntegrityError` is still a 500. It answers 503 `SERVICE_UNAVAILABLE`, `retryable`, `Retry-After: 5`, `Cache-Control: no-store`: the usual JSON envelope under `/api/`, otherwise a small localized page (`errors/unavailable.html`; needs no database and no sign-in) with the request id as its "Reference" and, for a GET, a Try again link to the same page; a POST gets "your last action may not have gone through" and a link to `/{locale}/login` (never a replay link — a write might have landed before the connection dropped; the link was `/{locale}`, a 404, until a real click found out). The log line `database_unavailable` carries the error CLASS only (an `OperationalError`'s message can hold SQL and parameters), the path, the method and the same `request_id`, so a reported reference can be found.
     - *Session cleanup* (`get_session`): a request that waits on a slow network call (storage upload, AI) holds its connection idle and a pooler or router may reset it; the rollback at cleanup then raised AFTER the response was sent ("Caught handled exception, but response already started"). The close failure is logged (`session_close_failed`, class only) and swallowed; an error from the request itself still propagates untouched.
     - *Fewer round trips* (each is a network round trip, ~1 s on that route): a patient's id is looked up once per request (`deps._load_actor` calls `remember_patient_id`, kept in `session.info`; `documents/service.py::_patient_id` uses `remembered_patient_id` first; it still comes from the verified user id every request and every query still filters by it; a failed lookup is never remembered). A web upload costs 14 round trips (was 17): `process(..., known=doc)` takes the document `create_upload` just returned instead of re-reading it (`_owned_or_known` still checks the id and the caller's own patient, and an expired object is read, not trusted), and after a Core UPDATE the in-memory `doc` is patched with `set_committed_value` rather than `session.refresh` (`_bring_up_to_date`; it reads back if the session expired the object). The pipeline has always needed a session that keeps loaded values at commit (`SessionFactory` has `expire_on_commit=False`; `job.id` is read after the first commit). The documents list page went from 12 queries to 8. `tests/test_upload_roundtrips.py` pins the counts.
     - *A storage failure says why*: `storage.describe_failure(exc)` returns the exception class, the class of its root cause (`gaierror` = DNS) and the HTTP status if the store answered — never the message, key or bytes — and every `document_storage_{put,get,delete}_failed` warning logs it, so a 502 can be told apart (DNS / timeout / refused / bucket problem).
     - *Tests that need "today"* must use Pakistan time (`tests/test_documents.py::pakistan_day`: UTC+5 arithmetic, not the code under test). Two tests computed it in UTC and failed between 00:00 and 05:00 in Pakistan.
   - OAuth added no tables and no migration — "onboarding incomplete" is derived from the absence of a role row, not stored anywhere.
   - Before assuming any column/table exists, check the real schema (`information_schema` or the migration in `alembic/versions/`) rather than the original feature spec — the spec predates this reconciliation.

11. **Medical documents (FR10–FR13)**
   - One pipeline for all four types (prescription `rx`, lab report `lab`, vaccination `vaccine`, `other`): upload -> `uploaded` -> common OCR (`processing`) -> type-specific extraction -> `awaiting_review` -> **Confirm & Save** -> `finalized`. Only `extractors.py` varies by type. Never add per-type endpoints or per-type tables.
   - **An upload is never a record.** Every record list reads `status == 'finalized'`. State transitions (claim for processing, confirm, cancel) are single conditional `UPDATE`s so a double-click or a concurrent cancel cannot start OCR twice or resurrect a cancelled upload. Confirm is idempotent.
   - Reuses the shared `document` / `ocr_job` / `ocr_extraction` tables and the private `medical-documents` Storage bucket (originals are served back only through the ownership-checked `/file` routes). `ocr_extraction` keeps `extracted_value` (never overwritten) beside `corrected_value`; `row_index` groups the fields of one medicine / lab result. `document.doc_type` uses `vaccine` because the column is `varchar(10)`.
   - The app connects as `postgres` with BYPASSRLS, so — exactly like the patient profile — every query in `documents/service.py` filters by the caller's own `patient_id`; a foreign / missing id is the same `NotFound`. Patient identity comes from the session only.
   - `documents/ocr.py` is the single OCR entry point (`run_ocr(data, mime)`) and OCR is **entirely local, free and keyless** — no API key, no paid or external service, no document leaves the machine. **Only printed documents are read, by Tesseract** (`ocr_job.engine = 'tesseract'`). **Handwriting support (TrOCR) was deliberately removed on 2026-10-08** — the engine, its settings, `torch`/`transformers`/`sentencepiece`/`protobuf`, the model-download script, the upload/retry mode choice and the `ocr_mode` API field are gone, and the upload page says "Printed documents only". The shared `document.ocr_mode` column and its CHECK constraint (and `ocr_job.engine`'s `'trocr'` value) still exist in the database and were NOT migrated; the app always writes `printed`, and a document an earlier version had marked handwritten is simply read as printed on retry. Never add per-type OCR paths, and do not bring a handwriting engine back without being asked. PDFs are rendered to images locally with pypdfium2, page by page, under `OCR_MAX_PAGES`/`OCR_MAX_PIXELS`, and Tesseract runs on the thread pool (never on the event loop). OCR output is only ever a proposal: it goes through the review/edit screen and explicit Confirm & Save — never finalize OCR output automatically. Tests replace `ocr.get_engine` (pipeline tests) or fake only `pytesseract.image_to_data` (the ONE call per page that returns both text and per-word confidence — `ocr._read_page` rebuilds the text from it, byte-for-byte equal to `image_to_string`, enforced by a parity test; boundary tests in `tests/test_document_ocr.py`, which also has real-Tesseract tests that skip when the binary is absent); `tests/fakes.py`'s `FakeStorage` stands in for Supabase Storage. Never fake OCR success in production code: engine missing -> `OcrError('ocr_unavailable')` -> the document is `failed` and can be retried. `errors.ocr_model_unavailable` is kept in the catalogue only so a document that failed under the old handwriting reader still explains itself. OCR text and extracted values are clinical text: never log them or put them in `audit_log.detail`.
   - **Per-line confidence** (`OcrResult.line_confidences`: a list aligned 1:1 with `text.splitlines()`, each entry a `LineConfidence(geo_mean, min_prob)` or `None` for a blank page-separator line). It comes from Tesseract's per-word `conf`/100 in the same single `image_to_data` call. Nothing consumes it yet (not the badges), and it is not a safe truth signal on its own.
   - **Drug-name suggestions** (`drug_names.py`; the Review page only, the medicine field only): a small LOCAL list of generics and common Pakistani brands, fuzzy-matched (difflib, threshold 0.72) against the OCR'd name. Suggestions only — never auto-applied, never written to `extracted_value`, always shown BESIDE the patient's own editable text. A name that already exactly matches a known one gets none (so "Atorvastatin" is never second-guessed with "Rosuvastatin"); when two or more known names are within 0.08 of the best score ALL are shown, never one guessed winner (look-alike/sound-alike names are a medication-error risk; Losec/Lasix are bundled on purpose). Representative, not verified against DRAP, and not an external service.
   - **Extraction and certainty rules learned from real scans.** Frequency accepts `1+1+1` as well as `1-0-1`, and spelled-out counts ("three times daily") are matched whole. General advice written under the medicine list ("Drink plenty of fluids", "Avoid oily food for 2 days") closes the last medicine's block (`extractors._ADVICE_PROSE_START`), so a stray "for 2 days" can never become its duration. `normalization.py` never gives HIGH to a value with embedded junk, a garbled number or a full-sentence shape. Unambiguous junk list markers are stripped and the row flagged uncertain ("@) Amoxicillin", "&, Losartan", "( D Paracetamol"); shapes that could be real names are only FLAGGED, never rewritten ("G. Amoxicillin" vs "B. Complex", "db Metformin"). A dosage whose unit is not a real unit ("500 ag", "20 mq") is flagged uncertain and never auto-corrected — guessing a dose unit is exactly the silent fix this pipeline refuses to make.
   - **Section extraction rules learned from real scans** (all in `sections.py`, each with a regression test built from the actual OCR lines). Tesseract reads a multi-column letterhead in its own order — the address column can come BEFORE the name, and the name can share a line with a phone fragment or logo noise — so the facility name is cut at the first address/phone/digit/stray-symbol token (`_tidy_facility_text`), a logo glyph glued onto an all-caps name is dropped, and a name stacked over two lines is rejoined only when its first word is generic ("Medical Centre") and one lone capitalised word sits within two lines above it. Never assume line order. OCR garbles separators: `=`, `|` and `;` count as label separators for the patient block (not for dates: `|` is a table divider), and a label with NO separator ("Date 10-08-2026", "Patient ID 2026-7890", "Doctor Dr. X") is still a label, but only when a date, an id-shaped token or "Dr." follows — never for ordinary words ("Date of birth", "Patient advised"). Advice stops at sign-off lines ("For any queries...", "Get well soon!") and at a signature line with OCR scraps in front ("P. J Dr. Ayesha Malik"), joins a wrapped bullet, trims junk tokens from its edges and drops fragments under three letters — but keeps "Contact the clinic if...", "See Dr. Ahmed...", "2 glasses of water daily" and "Go to ER".
   - Extractors are deterministic regular expressions (uploaded text is attacker-controlled; no model ever acts on it) and only produce fields the shared schema models. Do not invent clinical fields for vaccination documents. An `other` document is read for medicines with the prescription reader but held to a STRICTER standard (`extractors.extract_other`): a row is kept only if its dosage is a real medicine dose (mg, mcg, g, ml, IU — not `%`), and never if the medicine's source line carries a laboratory unit (`mg/dL`, `mmol/L`, `U/L`) — the prescription reader strips `/dL` from the dosage, so the ORIGINAL line has to be checked. Without that, `HbA1c 7.2 %` or `Glucose 142 mg/dL` became a medicine. A medicine named without a dose is left for the patient to add.
   - **AI understanding is a provider chain, not one vendor.** `ai_understanding.py` asks `ai_providers.py`'s chain — Gemini, then Groq, then OpenRouter (`AI_PROVIDER_ORDER`; each is opt-in via its own key and skipped when unset) — for the first usable answer, so one provider's quota running out no longer switches the layer off. A provider that hits a rate limit/quota is skipped for `AI_PROVIDER_COOLDOWN_S` (a bad key/model for longer, a timeout briefly) so an exhausted free tier costs one failed call, not one per upload; the whole chain is bounded by `AI_TOTAL_TIMEOUT_S`. Every provider gets the same schema and safety instruction, and every answer goes through the same deterministic `_reconcile` checks — a fallback model is held to exactly Gemini's standard. When every provider fails, the deterministic extraction already computed is used, so uploads never fail because of this layer. Only OCR TEXT ever leaves the machine (never pixels); keys/prompts/responses are never logged. `tests/conftest.py` blanks all three keys and the cooldown ledger for every test — a developer's real keys must never reach the network from the suite. This layer is the only place document text leaves the machine; OCR itself stays local. Free model ids rotate: the current defaults were chosen from each provider's live model list when the chain was set up, because the first ones hard-coded from memory had already been retired — if a provider answers 404, fix `OPENROUTER_MODEL` / `GROQ_MODEL`; the chain just skips that provider meanwhile. `AI_SECTIONS_ENABLED=false` switches off the second (sections) call alone to save free-tier quota.
   - **Doctor-written prescription (API only; no screen calls it yet).** `POST /api/v1/doctor/prescriptions` (`documents/doctor_router.py`, `service.create_doctor_prescription`): a verified doctor (`VerifiedDoctorDep`, same write budget via `DoctorDocumentWriteRateLimit`) sends already-structured medicines for a patient; there is NO OCR and NO patient review — the medicines go through `normalization.normalize_prescription_rows`, are stored as an `OcrJob` with `engine='doctor_entry'` (migration `35c4bc13fa37`) and the document is finalized in the same call, then read back through the SAME patient endpoints (`GET /api/v1/documents...`). The AI layer only VALIDATES it (`ai_understanding.validate_doctor_prescription` may downgrade a field's certainty, never rewrite what the doctor typed). `uploaded_by` is the doctor, so the patient can never delete it (`can_delete`). **KNOWN GAP — fix before any UI calls it:** `create_doctor_prescription` checks only that the patient exists; there is no consent grant or doctor-patient relationship check (the consent gateway, `consent_grant`, is on `main` from PR #5), so any verified doctor can write a finalized prescription into ANY patient's record by id.
   - **Document management (search, open / download, delete, retry).** All of it is on the existing pipeline — no new table, no migration.
     - *Search and filters* (`documents/filters.py`, one parser for the API and the pages): `q` (a part of the file name, or of a document TYPE's name in either language — type names only for 3+ characters, or two letters would match every type), `type`, `status` (`uploaded|processing|awaiting_review|failed|finalized`; `cancelled` is never listed), `date_from` / `date_to` (the document's own date, else its upload day; both ends included). **Days are Pakistan days**: timestamps are stored in UTC, but the upload day a patient sees, filters on and is ordered by is the UTC+5 calendar day (`db/sqlfuncs.py::pk_date` — a SQL function with a PostgreSQL `AT TIME ZONE 'Asia/Karachi'` form and a SQLite one — and `db/types.py::pk_date` / `web/documents.py::_local_date` for a value already in Python), so a document uploaded at 01:00 on the 10th in Pakistan is the 10th, not the 9th. The saved list is ordered by document date (else upload day) newest first, then `finalized_at`, then id — the id makes the order total, so pages over tied dates never repeat or skip a row. **Paging**: the API takes `limit` (1 to `MAX_PAGE` = 500, default 500) and `offset` and answers the total in `X-Total-Count`; the page has 25 per page (`?page=`, a non-number or out-of-range value is page 1 / the last page), and the in-progress section is capped at 100 rows with a note saying so. **The API refuses what it does not know**: an unknown query parameter is 422 `errors.unknown_parameter` (a misspelt `statuss=failed` must not silently return everything), and `/in-progress` takes `status` too. They combine; every query still starts from the caller's own `patient_id`; `%` and `_` in a search are ordinary characters. An invalid value is REPORTED, never guessed at: the API answers 422 naming the field, the list page ignores it and says so. The list page (`web/documents.py::_render_list`) keeps the filters in the address (bookmarkable; the auto-refresh while a document is `processing` keeps them), keeps the type tabs working with the other filters set, and has its own empty / no-match / invalid-filter states. Not searchable, by design: the facility / doctor / patient names, which are read from the OCR text each time a page is built.
     - *Original file*: `GET .../file` (API and page) serves the stored bytes exactly as uploaded, `inline` to look at or `attachment` (`?download=1` on the page, `?download=true` on the API) to keep a copy — never a preprocessed image, never OCR output, never a public storage URL. `storage.is_missing()` tells "the object is not there" (`NotFound`, one answer for a foreign id, an unknown id, a deleted document and a lost file) from "the store would not answer" (`FileUnavailable`, 502, retryable); the page shows a banner in either case rather than a bare 404.
     - *Delete* (`service.delete_document`; `DELETE /api/v1/documents/{id}` and `GET|POST /{locale}/patient/documents/{id}/delete`): for every status except already-deleted. What goes: the stored file, `ocr_text`, every `ocr_extraction` cell, `ocr_job.ai_sections`, the file name and the document date. What stays on purpose: a TOMBSTONE row (`status='cancelled'`, the state a discarded upload already has — never listed, never served; `finalized_at` is kept so it still says it was once a saved record) so the `document.delete` audit entry (ids, type and previous status only — never the name or any value) still points at something; and everything the document ALREADY put elsewhere — an allergy it added to the profile is the patient's own profile entry and is removed only from the profile page. Rules, all enforced in the service: ownership; a SAVED record needs `confirmed` (`?confirm=true` / the ticked box) and must have been uploaded by the patient — a clinician-authored record (`uploaded_by` is not the patient) is `DocumentNotDeletable`, like a profile entry's `recorded_by` — and `DOCUMENT_ALLOW_DELETE_FINALIZED=false` turns off deleting saved records altogether; deleting a deleted document is a no-op. **Order matters** (no false success, no orphaned file), and it is ONE routine for both delete and discard — `service._retire` (`_tombstone` is its database half): (1) one conditional UPDATE claims the row (taking its row lock, so a concurrent confirm / retry waits and then finds it gone, and a document confirmed in the meantime is `InvalidDocumentState` with its file untouched) and the audit entry is written, all uncommitted; (2) `storage.remove()` — which RAISES, unlike the best-effort `storage.delete()` — must confirm the file is gone, else everything is rolled back and `DeleteFailed` (502) is raised with nothing changed; (3) only then commit. A commit that fails after (2) would leave the record pointing at nothing, so the database half is done AGAIN once in a fresh transaction (an ambiguous failure — the first commit had landed after all — is recognised and not audited twice); only if that fails too is `DeleteFailed` raised, and deleting again finishes the job (removing a missing key is not an error). **Discard** (`cancel`) uses the same routine with `scrub=False` (it keeps the file name and date, which a delete forgets), so it too no longer leaves an orphaned file — and, as a consequence, it now fails with `DeleteFailed` while the file store is down instead of reporting a success that left the file behind. `backend/ops/scripts/purge_cancelled_files.py` (dry run by default, `--apply` to remove) clears the files the OLD best-effort discard left behind. This path (ILIKE + `ESCAPE`, `pk_date`, paging, the row lock against a concurrent confirm, in both orders) was also run against a real PostgreSQL 16 — the unit suite is SQLite. The confirmation step works without JavaScript (a page) and with it (one `<dialog id="delete-dialog">` per page, filled in by `documents.js` from the trigger's `data-delete-*`; `partials/doc_delete.html`). Static files have no cache-busting: a browser holding an old `documents.js` simply falls back to the confirmation page.
     - *Retry*: `POST .../process` (unchanged — atomic claim, stale-`processing` recovery, previous proposals reset, `finalized` refused, `awaiting_review` returned as is). `DocumentOut` now carries `can_retry` (only `failed`), `can_delete` and `can_download`, decided by the server (`service.can_retry` / `can_delete` / `to_out(doc, owner_user_id)`), so a control is shown only when the action would be accepted — and the server checks again. The list has a "Try again" button on failed rows. A failure code with no message of its own shows the general one (`web/documents.py::_failure_text`), never a catalogue key. The old "handwritten OCR mode" does not exist (TrOCR was removed): a retry reads the preserved original as printed.
   - **Photo quality — "please upload a clearer photo"** (`ocr.assess_quality`, `service.remember_quality` / `quality_of`, `partials/doc_quality.html`; ADVICE only, never a gate). A blurry page does not fail loudly — Tesseract returns plausible WRONG text — so the page the engine would receive (`_pages`, as the preprocessing report) is measured and the patient is told on the review page, the failed page AND the `uploaded` page (an upload not yet read), with a button to upload again with the same document type pre-chosen. Issues, in fixed order: `blank` (no ink / no contrast; only when EVERY measured page is blank — a blank back page is normal), `blurry` (`_sharpness` < `_BLURRY_BELOW` = 0.42), `faint` (contrast < 25), `low_resolution` (an image's long side < 800 px, from `_source_facts`). `_sharpness` is the weaker of the horizontal and vertical edge strengths, each the 90th percentile of the gradients of the page's EDGE pixels (those at least 10 % of the ink-to-paper contrast; fewer than 200 of them = too little writing to judge) over that contrast, on the page scaled to <= 1600 px: per DIRECTION because motion blur leaves the edges along it sharp, relative to contrast so faint-but-sharp is not called blurry, relative to the page so camera resolution does not matter. **Learned the hard way — calibrate on BOTH dense and sparse pages.** The first version (a percentile over ALL pixels, calibrated on dense pages only) read every sparse sharp page — a short certificate, a vaccination card — as blurry, because on a page with little writing that percentile lands on blank paper; a fixed count of the steepest edge pixels fixed that but let a few surviving sharp edges hide real blur on a dense page; the percentile of the EDGE pixels is the one that held on both. **The thresholds are measured, not guessed** — synthetic scans, dense AND sparse (1-6 lines on an A4 sheet), degraded (Gaussian 0.6-4 px, motion 5-15 px, low resolution 500-1300 px, JPEG q10/30, faint ink, a soft photo) and read by real Tesseract (~180 reads): sharp pages never scored below 0.51 (sparse 0.51-0.62, dense 0.61-0.76; none of 20 flagged); Gaussian >= 1.4 px, motion >= 5 px and a soft or ~500 px photo were flagged on 17-20 of 20 pages, where Tesseract's read starts to fall away (Gaussian 2 px: median word recall 80 %, motion 9 px: 9 %); 0.6 px blur (read at 90-100 %) was never flagged; uniform fading barely hurt Tesseract, hence the low `faint` bar. They are named constants in `ocr.py` with the calibration written beside them; real phone photos may sit differently — recalibrate the same way. Only the first `_QUALITY_MAX_PAGES` = 3 pages of a long PDF are measured. Images are converted to grey by `_to_grey` (transparent PNG flattened onto white, 16-bit / float modes stretched to 0-255 — a naive `convert("L")` read a 16-bit scan as blank). **No migration:** the verdict is measured ONCE, in `process()`, CONCURRENTLY with the OCR read (about 1-2 % overhead; measuring first cost 25-50 %) while the original's bytes are in hand, and kept in the TTL cache (`doc_quality:{id}`, 6 h — a pure optimisation); a lost verdict is re-measured from the stored original the next time a review / failed / uploaded page or `GET /api/v1/documents/{id}` asks (`DocumentDetailOut.quality: {issues, sharpness, contrast} | null`), and when the original cannot be measured or fetched a short negative marker (30 s) stops every page view re-fetching the file. It is never computed for a list, a saved record or a deleted document, never fails an upload or a read, and never changes what is read. What it cannot use without a stored column: Tesseract's per-line confidence from the read itself (`OcrResult.line_confidences`) — storing the verdict (one nullable column on `ocr_job`) would let the check use it and cost nothing per view; that is a schema change and needs the user's approval first.

Anything else falls back to the role's dashboard. A visitor who is already signed in and opens `/login?next=...` is sent straight there. (Google sign-in does not carry `next`.)

Recomputed on demand, never stored, never calls an engine. Linked from the uploaded/failed/review screens only.

   - **A layout per document type (2026-10-10; `partials/doc_layouts.html`, dispatched by `detail.html`; macros `review_lab/vaccine/other` and `saved_lab/vaccine/other`; helpers `ds.block` / `ds.rows` / `ds.fields` / `ds.other_rows` / `ds.topics`).** Review and saved record are the same page shape. The raw OCR text is folded away when the page already shows what the document says and open when it is all there is (`raw_open` in `detail.html`; always folded for a prescription).
   - **Extraction behind those layouts** (each with tests). (a) `extractors.find_document_date` ranks its labels: the document's own date (report / issued / date / vaccination / discharge) beats another labelled date (collected / received / sample / specimen / next / due), which beats an unlabelled one; ties go to the earlier — so a report printed after its "Sample Collected" line is no longer dated the collection day, a discharge summary is dated by its discharge, and `Date of Vaccination:` now counts as a label. A "Report Date" label left dangling (a two-column header read column-wise) takes the first later line that is nothing but a date (`find_detached_report_date`; `sections` reads it as `report_date` for lab reports) — measured on the synthetic CBC scan, which had printed a report date the sections used to miss. (b) `sections._facility_names`: a lab report and an "other" document sort the names they carry into `hospital_name` / `lab_name` (laboratory words -> lab; a hospital printed beside a laboratory is a second field; a lab-report name with neither kind of word stays `lab_name`, as before); a labelled "Hospital: / Lab Name: / Facility:" beats a guess (a "Collection Centre:" or "Lab No:" is not a facility); a first line that is the document's TITLE ("Medical Certificate", "Complete Blood Count", "Immunization Card") is never a facility for anything but a prescription; a line with a colon, a tagline or more than six words is not a second name. A prescription and a vaccination card keep one `hospital_name`. (c) `sections._extract_topics` (other documents only): a heading the document printed (Findings / Observations, Conclusion, Procedure, Hospital course, Treatment given, Condition at discharge — it must end in a colon or dash or stand alone, so "Findings were discussed" is not one) opens a passage that runs to the next heading, labelled field, signature or footer (at most 12 lines): the document's own words, never summarised and never replaced by the AI reading. `Recommendations` and `Discharge advice / instructions` are notes headings. (d) `vaccines._from_key_values`: a certificate written as `Vaccine: / Dose: / Date of Vaccination: / Batch No: / Site: / Next Dose Due:` lines is read as complete doses (a `Vaccine:` label opens a dose; facts printed ahead of the first vaccine join it only when it is the only dose; a bare `Date:` counts only inside a dose block); it is used only when it found a dose with at least one fact beyond the name — otherwise the line and table readers run exactly as before.
   - **Advice is its own section.** `sections.notes` (read-only, recomputed from the OCR text — NOT stored as rows; storing/editing it would be another migration) is shown under the heading "Advice" (`documents.section.advice`; a lab report keeps "Notes / Interpretation"), once, directly after the tables in review and after them on the saved record — no longer inside the "Other details found in your document" block (a block that no longer exists: lab reports, vaccination cards and "other" documents show their own details in their own layouts).
   - **Sections are bounded, not swept — and every document type has them.** `sections.py::structure_document` handles prescription, lab, vaccination and other. All get facility / patient / doctor / document dates / notes; on top of that a prescription and an "other" document get **vital signs** (`vitals.py`), a lab report and an "other" document get a **document title** (`document_title`), and a vaccination record gets its **vaccine doses** (`vaccines.py`). The patient's date of birth (`date_of_birth`) is a patient field. It finds the facility name from the letterhead by what it is (strong nouns: hospital/clinic/centre/lab...; handles doctor-first letterheads and a name wrapped over two lines), reads age and gender independently, and keeps the advice section to ADVICE: it starts at a heading (a notes word merely inside a medicine line is not one) and ends at a medicine line, another labelled field, the signature or page-footer text; advice with no heading is found after the last medicine (`extractors.looks_like_general_advice`). `sections` are recomputed from `document.ocr_text` each time a page is built (and shown while a document is `awaiting_review` AND once `finalized`); `service._sections_out` splits `complaint`/`diagnosis` out of the report items into a `clinical` ("Symptoms & Diagnosis") section. **What a reviewable table holds is NOT repeated there:** diagnosis, symptoms, vital signs and vaccine doses are TABLES now (see "Reviewable tables" below), so `_sections_out(..., covered)` hides the computed copy of any table that has stored rows — and falls back to the computed section for a document saved before the tables existed (no cells for that table), so old records lose nothing. A bare `symptoms` is only a label with a colon ("for allergy symptoms. if" is a sentence). An optional AI reading of the sections (`ai_sections.py`, `AI_SECTIONS_ENABLED`) is a SECOND provider-chain call per upload (all four types), run concurrently with the medicines call at processing time and stored in the nullable `ocr_job.ai_sections` JSON column (migration `b7e24c19a053`; reset on every retry; NULL = none, and the page shows the deterministic sections exactly as before). The model only POINTS at text already on the page: every value is stored only if it is evidenced in the OCR text (a decimal like `98.6` is ONE token, so `98` is not evidence for it; a number written with separators — `27-09-2026`, `120/80` — must appear whole and in order, so rearranging its parts is refused; ordinary words within a one-letter OCR slip, advice at least 80%), within the field's length cap, in the `sections.py` vocabulary — anything else is dropped, never shown. `sections.apply_ai_sections` merges it over the deterministic result: free text (names, address, complaint, diagnosis, title) takes the validated AI reading, fixed-shape values (id, age, gender, date of birth, phone, e-mail, dates, every vital) keep the extractor's reading when it has one, a vaccine-dose table is never mixed (deterministic if it found any, else the AI's), and stored JSON is re-validated for type/key/length because it is data, not trusted code. The lab `provider` section keeps `referred_by` (the doctor who SENT the patient: "Ref. By:") apart from `doctor_name` (who wrote/signed it) — never merge them.
   - **Reviewable tables (`groups.py`) — one pipeline, several tables of rows.** A document's rows are `ocr_extraction` cells grouped by `row_index` (a row = the cells sharing one index); a TABLE is the set of field names that belong together, and no field name belongs to two tables, so a row's table is always recoverable from its fields. Per type: prescription = medicines, diagnoses, symptoms, vitals, allergies; lab = results; vaccination = vaccines (doses); other = the SAME five as a prescription (read for medicines by the stricter `extractors.extract_other`, below). The vital signs are a table like the others: shown in review (all nine inputs), corrected there, stored on Confirm & Save, and listed on the saved record only for the vitals that have a value. `groups.ALL_FIELDS` is the single list of allowed field names and `tests/test_migration_field_names.py` asserts the migration's CHECK equals it — a new field needs a migration first. **Each table owns a block of `row_index` values** (`INDEX_BLOCK = 1000`: medicines/results/vaccines 0.., diagnoses 1000.., symptoms 2000.., vitals 3000.., allergies 4000..), so a client that adds a medicine at "the next index" can never land on another table's row (the first version numbered rows sequentially across tables and exactly that collision appeared). The vital signs are a `layout="list"` table: ONE row whose nine fields always exist as cells, found or not, so any can be filled in. `DetailOut.rows` / `field_names` still mean the PRIMARY table (medicines / lab results / vaccine doses); `groups` carries every table. Rows other than the primary table's come from `proposals.extra_rows` (sections + the merged AI reading), written at processing time, never auto-confirmed.
   - **The confirm contract (`service.confirm_with_outcome`).** `ConfirmRequest.groups` names the tables the request REVIEWS: for those, a row left out is a row the patient removed; a table NOT named is left exactly as proposed — stored, never marked `reviewed_at` — so a client that only knows the medicines can never silently erase the rest (omitted `groups` = the primary table only; the web page sends all). A row must belong to ONE reviewed table, sit in that table's own block of indexes, and (if it already exists) keep the table it was proposed in; each table has a row cap, and an empty "add a row" line counts for nothing. A prescription / lab report must still keep ≥1 row in its primary table (`groups.min_rows(doc_type, table)` — per document TYPE, so an `other` document, whose primary table is also the medicines, can be saved with none). A corrected value is stored beside the proposal (`corrected_value` vs the never-overwritten `extracted_value`), exactly as for medicines.
   - **Allergies reach the patient's profile only through Confirm & Save.** A reviewed allergies table adds each KEPT row to THAT patient's `allergy` list via `profile.service.add_allergy` — the same service the profile page uses, so the same rules apply (a duplicate is refused, there is a cap, the entry is audited, and `recorded_by` = the patient so they can edit or remove it later). It runs AFTER the document is saved, in the profile service's own transactions, so one allergy that cannot be added (duplicate, list full, invalid) never undoes the document or blocks the rest; the outcome (`ConfirmOutcome.allergies_added / allergies_skipped`) is shown on the saved page. A severity outside mild/moderate/severe/unknown is dropped, not guessed; the allergy is still kept. `document.confirm`'s audit blob records only a COUNT (`allergies_confirmed`), never what the allergies are. The reader (`sections._extract_allergies`) is strict because this writes to a safety record: only a real label opens it (`Allergies:`, `Known drug allergy:`, `Allergic to ...` — never the word inside a sentence: "for allergy symptoms. if"), and "NKDA / No known allergies / Nil / None" proposes nothing. The AI layer may propose allergies only where the text itself says so: each must be evidenced on an ALLERGY line (`ai_sections._allergy_context`), not merely somewhere on the page — otherwise a model could "find" an allergy in any medicine the prescription names.
   - **Vitals** (`vitals.py`): one regex per vital, anchored on its LABEL and capturing only a value of that vital's shape — BP, pulse, temperature, respiratory rate, SpO2, weight, height, BMI, blood sugar. Proposed as written (a unit only if the document printed one; nothing converted); first occurrence wins; in a fixed order — proposed in the vital-signs table, reviewable and editable. An impossible reading (BP 12/80, pulse 7) is dropped, but the limits are deliberately wide (BP 280/160 must show). Every number pattern must END where the number ends (`(?!\d)`): `BMI: 300` was once read as `30` — a truncated number is a plausible wrong value, the worst kind.
   - **Vaccine doses** (`vaccines.py`): a line is a dose only if it NAMES a vaccine (EPI/travel list matched as written); dose/date/batch/site/next-due come from labels, shapes, or a table's own header row; a column the card doesn't show is absent, never filled; a sentence that merely mentions a vaccine is not a dose.
   - **Lab flags** (`lab_flags.py`; High / Low / Normal / Abnormal / Critical / Check): worked out when a row is read and **never stored** (`RowOut.flag`, `flag_source`). Order: the report's own printed marker (`H`, `L`, `HIGH`, `*`, `230H`, an arrow — single letters must be UPPER case) if the result beside it was not edited, else calculated from a plain-number result and a stated range, labelled "calculated". A thousands separator is part of the number (`150,000-450,000`; reading it as `0-450` once flagged a normal platelet count High). **`check` is not a verdict:** a result out of a BOUNDED range that would sit inside it with a decimal point restored (RBC `46` vs 4.2-5.4, Hb `128` vs 11.5-15.5) is shown as "Check value" — the scan most likely dropped the point, and a confident wrong flag is worse than none. It is NOT applied to a single limit (`<150`), where dividing any high value by ten lands under it. The review step shows the pill under the Result input; the saved record has a Flag column.
   - **Lab table layout** (`service._read_document`): Tesseract's default `--psm 3` reads a results table column by column, so the Reference Range column comes out as a separate block far from its rows (and decimals can be lost). A lab report whose first read left some rows without a range is read once more with `ocr.run_ocr(..., layout=ocr.LAYOUT_TABLE)` (`--psm 4`), and that read is adopted only if it recovers STRICTLY more ranges without losing rows (or the first found no rows at all). Never for another document type (`--psm 4` reads those worse); a failed second read can never fail the upload. On the synthetic CBC scan this took 0 -> 13 of 15 rows with a range and fixed `128` -> `12.8`. `run_ocr` itself stays ignorant of document types.
   - **Fabricated-text guards (kept from the handwriting days).** `normalization._looks_like_fabricated_prose` / `_dosage_lacks_medical_shape` still refuse to give a high certainty to a medicine/dosage that reads like a full sentence — a cheap defence against any noisy OCR line that looks like fluent prose rather than a medicine. They were written for TrOCR's "confident hallucination", which no longer applies, but they cost nothing and are tested; do not remove them as dead code.
   - **Open items (as of 2026-10-11).** (1) The lab table re-read recovers most reference ranges but not all (a range OCR garbles — `(6)`, `O=2` — still gets no flag), and a decimal the scan dropped on a single-limit range (CRP `42` vs `<6.0`) is flagged High, labelled "calculated" — the review screen is the safeguard. The doctor's patient page reads through `load_doctor_patient_page`: ONE pass — one live access check, one `access_log` row per shared section (written before that section's data is read), each shared section read once (visits and lab reports as D2's typed records, the other sections as the compact rows), one `record.read` audit row, one commit, all or nothing. It replaced a `read_sections` + `load_patient_for_doctor` pair that checked access three times and read the profile sections and the visits twice; `tests/test_doctor_page_roundtrips.py` pins the cost (29 statements with every section shared, 16 with two; it was 42 and 26) and that an unshared section is never queried or logged. A visit lists its prescriptions only when the `prescriptions` section is shared too. `load_patient_for_doctor` (the full `PatientRecordOut`, for callers that want the typed record) checks the grant live (via `consent.service.patient_and_grant_for_doctor`), loads the record, writes one `record.read` audit row and commits both in one transaction — if the audit write fails the read is rolled back. Every denial is the same `NotFound`; every query filters by `patient_id` in application code (BYPASSRLS). Reads run sequentially on one `AsyncSession`.
   - `backend/app/clinical/schemas.py` holds the typed, read-only output (`PatientRecordOut` and its parts). Nothing in it is accepted as input.
   - The 8 clinical models in `db/models.py` — `Encounter`, `Diagnosis`, `VitalSign`, `Medicine`, `Prescription`, `PrescriptionItem`, `LabReport`, `LabResult` — map the wider product's live tables. They are read-only here: no migration, no writes. Each table is mapped ONCE and shared by D2 and the timeline (P3): a second `class Encounter(Base)` for the same table makes the whole app fail to import (`Table 'encounter' is already defined`) — extend the existing class instead.
   - An AST guard, `tests/test_consent.py::test_no_direct_clinical_queries`, fails the build if any file under `backend/` other than `consent/gateway.py` and `timeline/sources.py` (the timeline readers the gateway calls) calls `select(...)` on the guarded clinical models; the timeline's own guard (`tests/test_timeline.py`) allows the same two files plus `db/models.py`.
   - `backend/app/doctor/what_changed.py` builds the page's "What changed" panel: a deterministic diff (no LLM) of allergies, conditions and medications added/removed/resolved since the doctor's previous `record.read` audit row for that patient. The handler calls `last_read_at` **before** the gateway read, because the read writes its own `record.read` row.
   - The page is `/{locale}/doctor/patient/{patient_id}` (`doctor_patient_page` in `web/router.py`, template `doctor/patient.html`); the URL carries the patient id, never the passport number. Page tests live in `tests/test_doctor_patient.py`; its round-trip budget in `tests/test_doctor_page_roundtrips.py`. Rules and acceptance criteria are in `.claude/specs/d2_patient_history_spec.md` (BL-01…BL-14, AC-01…AC-18).

### When Making Changes

- **Authentication changes**: Focus on `deps.py`, `identity/`, and related tests. Never reintroduce a shared, stateful Supabase client across sign-in and admin operations (see Key Architectural Decisions above).
- **OAuth changes**: Read `identity/oauth.py`'s module docstring first — the `state`-param gotcha there is easy to reintroduce by accident if the Supabase SDK/API ever looks like it should accept one. Never provision a `Patient`/`Doctor` row before onboarding; never skip the email-collision guard in `login_with_oauth`.
- **Patient profile changes**: Read `.claude/specs/patient_profile_spec.md` first — it wins over `docs/TDD.md` wherever they disagree. Put every business rule in `profile/service.py` so the API and the web page stay in sync; never perform a query on `allergy`/`chronic_condition`/`patient_medication` without filtering by the caller's own `patient_id` (BYPASSRLS means the database will not catch a missed scope). Never let a patient edit an entry whose `recorded_by` isn't their own `user_id`.
- **Schedule changes (D7)**: Read `.claude/specs/D7-multi-hospital-schedule.md` first. Put window rules in `schedule/engine.py` (pure, no app imports) and call `engine.overlaps` — never write another overlap test. Never gate schedule routes with `VerifiedDoctorDep`, never read a `schedule_exception`/`doctor_schedule` row except through `doctor_affiliation` scoped to the caller, never hard-delete a slot or exception.
- **Consent / access changes**: Read `.claude/specs/privacy_access_spec.md` first. Never read another patient's sections outside `consent/gateway.py`; never return 403 for a consent failure (use `NotFound`/`ConsentDenied`); never update or delete `access_log` rows.
- **UI changes**: Work with Jinja2 templates in `frontend/templates/` and `web/router.py` (documents: `web/documents.py`)
- **Timeline changes (P3)**: Keep `events.py` free of database code and put every query in `sources.py` (the only reader of the visit / prescription / lab-report tables). Search covers only what the reader can read in an event (never headings or dates, never a doctor's file names — a search must not become an oracle for hidden data); a new filter must run on the events the gateway already authorised, never before it. Duplicate prevention keys on a schema link, never on a name or date. Never read another patient's sections outside `consent/gateway.py` — go through `service.load`, never around it. Never list an unconfirmed upload as an event, never show a field the record does not hold, never give a doctor a `document_id` or file link, and never date an event by its upload day. A new event kind needs a builder in `events.py`, a `KINDS` entry, a `SECTION_OF_KIND` entry, catalogue keys in BOTH languages, and tests; the catalogue test fails on a missing key.
- **Database access / resilience changes**: Read "Reaching the database" first. Every extra query is a network round trip (about a second on a far-away pooler), so add a query to a hot path only if it is needed; never add `pool_pre_ping`; keep the "outage" classifier narrow (a real bug must stay a 500); never retry an authentication error; never log SQL, parameters or exception messages from the database layer (class names only).
- **Medical Passport changes**: Read `.claude/specs/medical_passport_spec.md` first. Put every consent rule in `consent/service.py`; filter every grant lookup by the caller's own `patient_id`; never make a doctor-side denial distinguishable from "no such patient" (always the same `NotFound`); never put a passport number in a URL, log line, or audit row.
- **Doctor dashboard changes**: Keep `doctor/rows.py` pure — consent decisions belong in `consent/service.py`.
- **Patient history (D2) changes**: Read `.claude/specs/d2_patient_history_spec.md` first. Query clinical tables only in `consent/gateway.py` or the timeline readers it calls, `timeline/sources.py` (the AST guards enforce it); never make a denial distinguishable from "no such patient".
- **Database changes**: Modify `db/models.py` to match the *real* shared schema (verify against `information_schema` first) and write an additive Alembic migration by hand — never autogenerate
- **Configuration**: Update `settings.py` with appropriate validation guards
- **Testing**: Follow existing patterns in `tests/` using the fixtures in `conftest.py` and the fake Supabase double in `tests/fakes.py`. A test that needs "today" must use Pakistan time (UTC+5), never `utcnow().date()` — see `pakistan_day` in `tests/test_documents.py`. Any test asserting OAuth-disabled behaviour must `monkeypatch` `oauth_enabled` explicitly — `Settings` reads `.env` regardless of `ENVIRONMENT`, so a developer's local `OAUTH_ENABLED=true` leaks into the test process too.

### Working agreements for OCR / extraction / AI-layer work

- Never commit, push or open a PR unless asked. The repo uses TWO tiers: feature branches are merged into `dev` by pull request (`dev` is protected), and `dev` is merged into `main` only when development is finished — never merge a feature branch into `main`. Bring `dev` into a feature branch by MERGE commit (not rebase) before opening or updating its PR; the history is merge-PRs.
- A schema change needs the user's explicit approval first (anything that would need a new `ocr_extraction.field_name`, a new column or a widened CHECK is one). `e3a52c8d7f14` was approved and applied on 2026-10-08 (it is what lets diagnosis, symptoms, vital signs, allergies and vaccine doses be reviewed). The lab FLAG is still never stored (additive, hand-written Alembic only), and the migration is previewed (`alembic upgrade A:B --sql`) and the row counts recorded before it is applied.
- The FINALIZED branch of `frontend/templates/documents/detail.html` (the saved record) was off limits until 2026-10-08, when the user lifted that rule for the clinical-sections / lab-flag / vaccine-table work (it now renders `partials/doc_sections.html`). Treat any FURTHER change to the saved record page as needing the user's say-so again.
- Keep `run_ocr` decoupled from document type, and `run_ocr` / `OcrResult` backward compatible (new fields have defaults; never rename or remove). Do not replace Tesseract or add an OCR engine (handwriting was removed on purpose); keep Urdu (eng+urd) working; keep the size/pixel defences and every distinct error code.
- Synthetic or fully anonymized data only; never send pixels anywhere; only OCR text may leave the machine, and only through the opt-in AI layer.
- Document management (search / download / delete / retry) was requested 2026-10-10; deletion of a SAVED record is allowed for the patient's own uploads, with confirmation, and can be switched off with `DOCUMENT_ALLOW_DELETE_FINALIZED=false` — change that policy only on the user's say-so.
- Run the full suite after each step and report the real result; say plainly when a step did not help.

The application prioritizes security and correctness over convenience, with deliberate choices like per-request role verification, fail-shape-identical error responses, and app-level lockout tracking independent of the identity provider.
